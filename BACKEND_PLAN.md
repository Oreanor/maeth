# Backend Implementation Plan

## Goal

Build the first networked MVP for Google/web players:

- Vercel hosts the Vite frontend and REST API functions.
- Supabase provides Postgres and Google OAuth.
- Telegram auth and Telegram-specific invitations stay out of scope for this phase.
- The server is authoritative for multiplayer game state, move validation, and duel rolls.

## Architecture

### Frontend

- Use `@supabase/supabase-js` for Google sign-in and session persistence.
- Keep the existing local bot flow working.
- Add an API client that sends the Supabase access token as `Authorization: Bearer <token>`.
- Add multiplayer screens/flows incrementally:
  - create game;
  - invite/link sharing;
  - join game;
  - poll game state;
  - submit placements and moves.

### Vercel API

Use serverless functions under `api/`:

- `GET /api/me` verifies the current Supabase session.
- `GET /api/games` lists games for the signed-in user.
- `POST /api/games` creates a new game.
- `GET /api/games/:id` returns the current game state.
- `POST /api/games/:id/join` joins an open invited game.
- `POST /api/games/:id/actions` submits a player action.

The API should verify the user from the Supabase JWT on every request and use the Supabase service role key only on the server.

### Supabase

Use Supabase Auth with Google provider enabled. Store app-specific game data in Postgres tables:

- `profiles`: public player profile linked to `auth.users`.
- `games`: authoritative game row and serialized `GameState`.
- `game_players`: players, colors, and per-game status.
- `game_invites`: invite links and invite status.
- `game_actions`: append-only audit trail of placements and moves.

Enable Row Level Security for browser-readable data later, but keep game mutation logic behind Vercel API functions so move validation cannot be bypassed.

## Implementation Phases

### Phase 1: Project Setup

- Add Supabase client dependency.
- Add Vercel API types.
- Add `.env.example`.
- Add Supabase schema draft.
- Add shared API/auth helpers.

### Phase 2: Google Auth

- Replace mocked Google login with Supabase OAuth.
- Restore user from Supabase session instead of `localStorage`.
- Keep guest login for local/offline testing.
- Leave Telegram login as a disabled or stubbed future path.

### Phase 3: REST Game MVP

- Create authenticated Vercel API helper.
- Add game creation and fetch endpoints.
- Store initial `GameState` generated by the existing engine.
- Return player color and opponent metadata to the client.

### Phase 4: Multiplayer Actions

- Add placement action.
- Add move action.
- Reuse `placePiece`, `legalMovesFrom`, and `resolveMove` on the server.
- Persist updated `GameState` and append `game_actions`.

### Phase 5: Client Multiplayer UI

- Add API client functions.
- Add create/join flow from the lobby/friends screens.
- Add `/play/:gameId` or query-driven multiplayer route.
- Poll `GET /api/games/:id` while the game is active.
- Disable actions when it is not the current user's turn.

### Phase 6: Deployment

- Create Supabase project and enable Google OAuth.
- Add Vercel env vars:
  - `VITE_SUPABASE_URL`
  - `VITE_SUPABASE_ANON_KEY`
  - `SUPABASE_URL`
  - `SUPABASE_ANON_KEY`
  - `SUPABASE_SERVICE_ROLE_KEY`
- Run Supabase SQL schema.
- Deploy to Vercel and verify OAuth redirect URLs.

## Deferred

- Telegram Mini App auth and `initData` validation.
- Telegram deep links/start params.
- True friend graph import from external providers.
- Realtime subscriptions or WebSockets.
- Matchmaking and public lobbies.
